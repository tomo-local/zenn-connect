# 1. はじめに

はじめまして、tomo-localです。
最近、転職に伴ってメインで扱う開発環境が **Go から Ruby on Rails** へと変わりました。
GoからRailsに移って一番驚いたのは、テストの書き方だけでなく、テストに対する「思想」そのものが違うと感じたことです。
その中で、1ヶ月実務で触ってみて感じた言語の特性や、テストについての考えなど自分が感じたことをまとめてみたいと思います。

前職では、マイクロサービスでGoを使ったバックエンド開発をしていました。
Goは、コンパイル型の静的型付け言語で、シンプルで明示的な設計が特徴の言語です。
今回の転職では、Railsを使ったWebアプリケーション開発に携わることになりました。
Railsは、動的型付け言語であるRubyをベースにしたWebフレームワークで、規約に従った開発が特徴の言語です。

近年では、AIの進化により、言語やフレームワークの習熟度が低くても、ある程度のコード生成や補完が可能になってきています。
そのため、言語やフレームワークの習熟度だけでなく、
- 言語の特性を理解すること
- 言語に依存しない、ベースとなる知識を身につけること
が、より重要になってきていると感じています。

なので、今回はGoとRailsの言語特性の違いを整理しつつ、自分が感じたことについてまとめていきたいと思います。

# 2. 言語の特性

まず、GoとRailsの言語特性の違いについて整理していきましょう。

Goは静的型付け言語で、コンパイル時に型の整合性がチェックされ、厳格な型安全性が保証されます。
シンプルで明示的な設計が特徴であり、コードの可読性や保守性が高いです。

Rubyは、動的型付け言語で、柔軟で表現力の高い設計が特徴の言語です。
自然に言語を書くようなイメージのコードが書けるため、書きやすさや表現力の高さが特徴です。
また、Railsは、アプリ開発をするための基礎的な機能が揃っており、やりたいことを最小限のコードで実現できることが特徴です。
Rails Wayと呼ばれる、規約に従った開発が推奨されており、規約に従うことで、コードの可読性や保守性が高くなります。

# 3. テストについて

テストの考え方がGoとRailsの大きな違いの一つだと感じています。
自分の考えでは、Goのテストは、**「コードの正しさを保証するためのもの」**であり、input/outputの関係を明示的に定義することで、コードの正しさを保証することができます。
一方で、Railsのテストは、**「コードの振る舞いを保証するためのもの」**であり、コードの振る舞いを定義することで、コードの正しさを保証することができます。

Goのテストは、標準ライブラリに組み込まれており、シンプルで明示的なテストコードを書くことができます。
テストケースのstructを定義し、テーブル駆動テストを行うことで、テストコードの可読性や保守性が高くなります。
structにmockを定義することで、テスト対象のコードの依存関係を切り離すことができ、テストコードの可読性や保守性が高くなります。
ですが、Goのテストは、テストコードの量が多くなりがちで、テストコードの可読性や保守性が低くなることがあります。
AIを使用することで、テストケースを整理して自動生成することができるので高速でテストコードを作成することができます。
また、mockを使用する際にnilなどの値を返すことができるので、テストが正しく動作するかを確認できないことがあります。

```go
package foo_test

import (
    "testing"
)

func Test_Add(t *testing.T) {
    // テストケースの定義（テーブル）
    tests := []struct {
        name     string
        a, b     int
        expected int
    }{
        {"positive numbers", 2, 3, 5},
        {"negative numbers", -1, -1, -2},
        {"zero value", 0, 5, 5},
    }

    for _, tt := range tests {
        // サブテストとして実行
        t.Run(tt.name, func(t *testing.T) {
            actual := Add(tt.a, tt.b)
            if actual != tt.expected {
                t.Errorf("Add(%d, %d) = %d; want %d", tt.a, tt.b, actual, tt.expected)
            }
        })
    }
}
```

今の環境では、Railsのテストは、RSpecを使用しており、BDD（Behavior Driven Development）に基づいたテストコードを書くことができます。
RSpecは、テストコードの可読性や保守性が高く、テストコードの振る舞いを定義することで、コードの正しさを保証することができます。
テストケースを、`context` と `it` を使用して整理して書くことができ、適切な単位に分割することで、テストコードの可読性や保守性が高くなります。
ですが、let/before/let! で使用する変数を定義してコードを書くので、どこで定義された変数なのかが分かりにくくならないように注意して各必要があります。

```ruby
RSpec.describe 'Calculator' do
  describe '.add' do
    context 'with positive numbers' do
      let(:a) { 2 }
      let(:b) { 3 }

      it 'returns the sum' do
        expect(Calculator.add(a, b)).to eq 5
      end
    end

    context 'with negative numbers' do
      let(:a) { -1 }
      let(:b) { -1 }

      it 'returns the sum' do
        expect(Calculator.add(a, b)).to eq(-2)
      end
    end

    context 'when one number is zero' do
      let(:a) { 0 }
      let(:b) { 5 }

      it 'returns the other number' do
        expect(Calculator.add(a, b)).to eq 5
      end
    end
  end
end
```

# 4. 最後に

Railsの便利さや表現力の高さは魅力的ですが、1ヶ月実務で触ってみただけでは、まだまだRailsが自分に馴染んでいないと感じています。
基本的に、自力で書くのではなくAIに生成してもらったコードに対してレビューを行い、わからないところを質問して理解する、という形でコードを書いています。このやり方が正しいのかはわかりませんが、Railsのコードの書き方やテストコードの書き方を理解するためには、まずはAIに生成してもらったコードを理解することが近道だと感じています。

なぜ、自分でコードを書くのではなくAIに生成してもらったコードを理解することが近道だと感じているかというと、これからの時代に重要なのは特定の言語やフレームワークの習熟度ではなく、ベースとなる開発技術や知識を身につけることだと考えているからです。
なので、Railsを触りながらORMの内部の仕組みや、MVCの設計思想、テストコードの書き方など、言語やフレームワークに依存しない知識を身につけることが重要だと考えています。

Goで意識していたような「明示性」や「予測可能性」、そしてアーキテクチャやデータ構造といった**エンジニアリングのベースの知識（基礎体力）をしっかり深めていくこと**。それによって、どんな環境でも通用する全体的な底上げをしていきたいです。

まずは目の前のRailsと仲良くなりつつ、普遍的な体力をつけていくぞ！という気持ちで2ヶ月目も頑張っていこうと思います。

# 1. はじめに

転職に伴い、メインで扱う開発環境が **Go から Ruby on Rails** へと変わりました。

前職ではマイクロサービスでGoを使ったバックエンド開発をしていました。Goに慣れた状態でRailsを触り始めたとき、最初に感じたのは、うまく言葉にできない違和感でした。同じWebバックエンドなのに、何かが違う。でも、その「何か」がすぐには言語化できませんでした。

僕は、その違和感を言語化するために、「GoとRailsはそれぞれどんな思想で、何を解決しようとして作られたのか？」を調べてみました。すると、設計の出発点がまったく違うことがわかってきました（Goは言語、Railsはフレームワークなので厳密な比較ではないのですが、そこはご容赦ください。GoとRubyの言語仕様そのものの違いは、また別の記事で整理したいと思います）。

今回は、その調べた結果をもとに、GoとRails（ちょっとRubyも）の設計思想の違いを整理しながら、それぞれの良さだけでなく、逆に困った部分も含めて、使い所を考えていきたいと思います。

---

# 2. GoとRailsが解決しようとした課題

言語・フレームワークの設計は、必ず「解決したい課題」から始まっています。
Go と Railsは、解決しようとした課題がまったく違うため、設計思想も大きく異なります。

## Goが解決しようとした課題

GoはGoogleで生まれた言語です。Googleが直面していた課題は、**大規模な分散システムを、大人数のチームで長期間にわたって保守すること**でした。

チームが大きくなるほど、コードの読みやすさや予測可能性が重要になります。「このコードが何をしているのか」が一目でわかることと、「本番環境で意図通りに動くこと」を最優先に設計されました。

> Go was designed to address the problems faced in software development at Google.
> — [Go FAQ](https://go.dev/doc/faq#creating_a_new_language)

## Railsが解決しようとした課題

RailsはDHH（David Heinemeier Hansson）がBasecamp（当時37signals）を作りながら生み出したフレームワークです。その課題は**少人数で、速くWebアプリケーションを作ること**でした。

DHHが最優先にしたのは「同じことを何度も書かせない」こと。そのために生まれたのが、Convention over Configuration（設定より規約）という思想です。

> Convention over Configuration means that the developer only needs to specify unconventional aspects of the application.
> — [The Rails Doctrine](https://rubyonrails.org/doctrine#convention-over-configuration)

## 出発点の違いが方向を決める

| | Go | Rails |
|---|---|---|
| 生まれた文脈 | 大規模分散システム | 少人数のWebアプリ開発 |
| 最優先 | 予測可能性・明示性 | 開発速度・DRY |
| 設計の軸 | **明示性** | **規約** |

# 3. 明示性と規約：設計思想がどこに現れるか

## ルーティング

Goでは、どのパスにどのハンドラを割り当てるかを明示的に書きます。
なお、このように `GET /users` とメソッド付きでパターンを書けるのは Go 1.22 以降の `net/http` の機能です（[Go 1.22 Release Notes](https://go.dev/doc/go1.22#net/http)）。それ以前は自前でルーティングを実装するか、サードパーティ製のルーターを使うのが一般的でした。

```go
mux := http.NewServeMux()
mux.HandleFunc("GET /users", handleGetUsers)
mux.HandleFunc("GET /users/{id}", handleGetUser)
mux.HandleFunc("POST /users", handleCreateUser)
```

どのエンドポイントが存在するか、どのメソッドを受け付けるかがすべてコードに書かれています。前職ではgRPCを使っていたので、さらに`.proto`ファイルでリクエスト・レスポンスの型まで明示的に定義していました。

一方Railsでは、こう書くだけです。

```ruby
resources :users
```

この1行が、`index` `show` `new` `create` `edit` `update` `destroy` の7つのルートを自動生成します。Railsの規約を知っていれば、書かなくても「このルートが存在する」とわかる。これがConvention over Configurationの実例です。

## エラーハンドリング

Goはエラーを戻り値として明示的に返します。

```go
user, err := userRepo.FindByID(id)
if err != nil {
    return nil, fmt.Errorf("user not found: %w", err)
}
```

Goは静的型付け言語なので、エラーは関数の戻り値の型として宣言されます。コンパイル時点で「この関数はエラーを返す可能性がある」ことが確定しており、呼び出し元は戻り値としてエラーを明示的に受け取る形になります。無視するには`_`で握りつぶす必要があるので、「このコードは失敗するかもしれない」がコードにきちんと残ります。

ただ、この明示性には裏返しのコストもあります。`if err != nil` を呼び出しのたびに書くことになるので、本質的な処理がエラーチェックのノイズに埋もれがちです。前職でも、3行のうち1行が `if err != nil` という関数は珍しくありませんでした。明示的であることと、読みやすいことは必ずしもイコールではないと感じています。

Rubyは動的型付け言語なので、どの関数が例外を投げるかはコードを読んだだけでは事前にわかりません。正常系を中心に書き、異常系は`rescue`でまとめて処理するスタイルが取られることが多いです。コードがシンプルになる一方で、例外の発生箇所は実行時にならないと見えません。

実際に触ってみて詰まったのは、まさにこの部分でした。コードを読むだけでは「この処理はそもそもエラーになるのか」が判断できず、影響範囲を把握するのに時間がかかりました。さらに、読む側だけでなく自分で書く側になると、今度は「どう実装すればいいのか」というルールがないことに困りました。Goのように戻り値でエラーを明示するわけにもいかず、大きく`rescue`でまとめてしまうべきなのか、処理ごとに細かく`rescue`すべきなのか、チームに明確な指針がない中で判断するのは難しいと感じています。

## 依存関係の解決

Goではインターフェースを明示的に定義し、依存関係をコードで表現します。

```go
type UserRepository interface {
    FindByID(id int) (*User, error)
}

type UserService struct {
    repo UserRepository
}

func NewUserService(repo UserRepository) *UserService {
    return &UserService{repo: repo}
}
```

どのコンポーネントが何に依存しているかが、コードを読むだけでわかります。

Railsではこういったインターフェース定義やコンストラクタ注入は基本的に書きません。そもそも Rails は DI を積極的には行わず、必要なクラスをコード中で直接参照します。`UserService` の中で `UserRepository` を名前で参照するだけでよく、そのクラスが「どこにあるか」はファイル名とクラス名の規約に従って Zeitwerk オートローダーが解決してくれます。

> Rails can load your application's classes and modules on demand. This is known as autoloading.
> — [Rails Guides: Autoloading and Reloading Constants](https://guides.rubyonrails.org/autoloading_and_reloading_constants.html)

実際に詰まったのはここでした。あるクラスの挙動を理解しようとしても、そのファイル単体を読むだけでは完結せず、参照先のクラスを何個も行き来してようやく全体像がつかめる、という感覚に最初は戸惑いました。GoのようにインポートやDIで依存が明示されていないので、「このクラスは結局どこで何をしているのか」を追いかけるコストが読む側に寄っている、と感じています。

つまり Go が「何に依存するか」をインターフェースとコンストラクタで明示するのに対し、Rails は依存を直接参照しつつ「その参照先の在り処」を規約に委ねている、という違いです。

オートロード自体はよくできた仕組みですが、動いている理由がわからないまま動いてしまう場面もあります。`before_save` や `after_commit` のようなコールバックも同様で、どの処理がいつ実行されるのかをコードの見た目だけから追うのは難しく、暗黙的な副作用があちこちに散らばりやすいと感じています。

## テスト

テストにも、この設計思想がそのまま現れています。

Goはテーブル駆動テストが一般的です。入力と期待値を構造体に明示的に定義します。

```go
func Test_Add(t *testing.T) {
    tests := []struct {
        name     string
        a, b     int
        expected int
    }{
        {"positive numbers", 2, 3, 5},
        {"negative numbers", -1, -1, -2},
        {"zero value", 0, 5, 5},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            actual := Add(tt.a, tt.b)
            if actual != tt.expected {
                t.Errorf("Add(%d, %d) = %d; want %d", tt.a, tt.b, actual, tt.expected)
            }
        })
    }
}
```

RailsではRSpecを使ったBDD（振る舞い駆動開発）が一般的です。`context`と`it`で「どういう状況でどう振る舞うか」を自然言語に近い形で記述します。

> RSpec is a behaviour-driven development (BDD) tool for Ruby programmers.
> — [RSpec](https://rspec.info/)

```ruby
RSpec.describe 'Calculator' do
  describe '.add' do
    context 'with positive numbers' do
      it 'returns the sum' do
        expect(Calculator.add(2, 3)).to eq 5
      end
    end

    context 'with negative numbers' do
      it 'returns the sum' do
        expect(Calculator.add(-1, -1)).to eq(-2)
      end
    end
  end
end
```

GoのテストはGoらしく、RSpecはRailsらしい。テストの書き方にも、それぞれの設計思想がそのまま出ているのが面白いと感じています。

一方で、実際に読んでみて詰まったのもこのテストコードでした。Goのテーブル駆動テストはテストケースが一列に並ぶだけなのに対し、RSpecは`context`と`it`で階層的にグルーピングされます。加えてコード量も全体的に多くなりがちで、どこで何を検証しているのかを把握するために階層を追いながら読み解く必要があり、整理するのに苦労しました。

# 4. それぞれの使い所を考える

転職してから「GoとRailsどちらが良いか」という問いを立てることがありました。でも今は、それは問いの立て方が違うと思っています。

## Goの明示性が活きる場面

前職でGoを使っていたとき、チーム自体は少人数でしたが、複数のマイクロサービスが連携するシステムでした。「明示性」のおかげで構成がシンプルに保たれ、全体像がわかりやすかったのが助かりました。

- 複数のサービスがAPIで連携していても、チームの人数に関わらず境界をまたいで誰が読んでも同じように理解できる
- エラーの扱いがコードに明示されているので、本番で予期しない動作になりにくい
- インターフェースが依存関係のコントラクトになっているので、チームやコードベースが大きくなっても崩れにくい

ただしこれは書く量が増えるというコストとのトレードオフでもあります。要件がまだ固まっていない段階で明示性を求めすぎると、変更のたびに書き直す箇所が増えて、かえって身動きが取りにくくなることもあります。すべての依存をコンストラクタで注入する設計を徹底すると、`main.go` が数百行の初期化コードで埋まっていく、というのはGoでよくある壁です。

`net/http`や`crypto`のような基盤部分の標準ライブラリは手厚い一方、ORMやバリデーション、リトライ処理といったWebアプリでよく使う一段上の機能は標準ライブラリの範囲外で、結局サードパーティに頼ることになります。「依存を明示する」という思想の割に、依存先をどう選ぶかは開発者に丸投げされている、という矛盾を感じることがあります。言語仕様がシンプルであることも良し悪し両面あり、Enumやパターンマッチのような表現力がない分、他の言語なら簡潔に書けることを回りくどく書かざるを得ない場面もあります。

## Railsの規約が活きる場面

Railsに移ってからは、CRUDが中心のWebアプリを少人数で素早く動かすための「規約」のありがたさを感じています。

- `resources :users` の1行でルーティングが揃うように、書かなくていいコードが多い分、本来やりたいことに集中できる
- RSpecのBDDスタイルが規約の暗黙知を仕様として補ってくれるので、少人数でも仕様の共有コストが低い

実際、少人数で要件がどんどん変わるフェーズでは、この規約のありがたさが際立ちます。書かずに済むぶん、考えることに時間を回せる。

## 規約が効かなくなる場面：Fat Model問題

Railsの規約は、乗っている間は快適でも、外れた瞬間にコストが跳ね上がるという特性があります。特に顕著なのがFat Model問題です。

- ActiveRecordのモデルに、バリデーション・スコープ・コールバック・ビジネスロジックがすべて集約されていきます。Railsの規約は「どこにモデルを置くか」までは決めてくれますが、「モデルの中に何を書きすぎないか」までは決めてくれません
- `before_save` や `after_commit` のようなコールバックを多用すると、どの処理がいつ実行されるのかをコードを読むだけでは追えなくなります
- 肥大化したモデルはテストも書きにくくなります。1つのテストファイルが数百行になり、モックすべき依存も増えていきます
- 最終的には、Service層やForm Objectのような「Railsの規約にない」層を自分たちで設計し、命名して導入する必要が出てきます

ここは規約が助けてくれない領域で、明示的な設計判断が必要になります。つまりアプリが大きくなるほど、Goが得意としていた「明示性」寄りの判断を、自分たちで後から持ち込むことになるとも言えそうです。さらに動的型付けであることの代償も大きく、Goならコンパイル時に弾かれるようなミスが、Railsでは実行時、最悪の場合は本番環境で初めて発覚します。リファクタリングの安全性という点では、型を明示するGoの方に分があると感じる場面が多いです。

## 判断のものさし

迷ったときに見ているものさしの一つが、プロジェクトのフェーズです。仕様がまだ動きながら固まっていく時期はRailsの規約に助けられますが、Fat Model問題のように規模が大きくなるほど、Goの明示性が恋しくなる場面が増えていきます。

ただ、ものさしはフェーズだけではありません。チームの入れ替わりが激しいプロジェクトでは、暗黙知に頼る規約よりも、コードを読めば判断できるGoの明示性の方が引き継ぎコストが低くなります。逆にメンバーが固定されていて、お互いの前提が揃っているなら、規約に乗ったほうが速いことが多いです。

もう一つ見ているのが、壊れたときの影響範囲です。障害が一部の機能に閉じるなら、多少雑に書いても被害は局所的で済みますが、決済や認証のように失敗が全体に波及する処理には、Goの明示性で固めておきたくなります。

結局は「どんな課題を解きたいか」が先にあって、それに合う道具を選ぶということだと思っています。ただ、チームがすでに持っているコンテキストも現実的には大事で、Goに慣れたチームにいきなりRailsを入れるのは、それなりの学習コストが伴います。道具の選定は課題から逆算しつつ、チームの状況も含めて判断するのが現実的だと感じています。

# 5. おわりに

GoからRailsへ移って最初に感じた「なぜこんなに違うのか？」という違和感は、設計思想の出発点が違うというところに行き着きました。そして触っていくうちに、それぞれの良さだけでなく、明示性の裏にある冗長さや、規約の裏にある「外れたときの脆さ」も見えてきました。

今の職場ではコードの生成をAIに任せることが多いのですが、AIが出してきたコードの良し悪しを判断するには、設計の背景がわかっていないといけない、と感じています。「この規約に乗るべきか、外れるべきか」の判断は、Railsが何を解こうとしているかを知っていないとできない。そういう意味で、設計思想を読み解く力は地味に重要だと思っています。

正直、まだGoとRailsのどちらが自分に合っているのか、はっきりとした答えは出ていません。ただ、以前のように「違うから気持ち悪い」とは感じなくなりました。

最後は結局、それぞれのトレードオフを整理した上で、目の前の課題にフィットする方を選ぶしかないんだろうなと思っています。「どちらが優れているか」ではなく、「この課題にはどちらが効くか」で選べるようになったこと。それが、転職して一番大きかった変化かもしれません。
